## 1. 方針

1. **物理・ルール・スコアは自動テストで守る**。ゲームの面白さの調整（M4 以降）で、物理やルールを壊さないようにする
2. **リアルさは数値で測る**：参照シミュレーションの期待値（RES-02）と、AI 対 AI のリアリティ KPI（RES-03 §4）
3. **遊びやすさは人で測る**：プレイテストの手順と記録を決めておく
4. **PR ごとに CI を通す**（CONTRIBUTING §5）。`Source/` を追加した後は、C++ のビルドと単体テストを CI に加える

## 2. テストのレベル

| レベル | 内容 | 道具 | 実行する時 |
|---|---|---|---|
| L0 文書 | リンク・Mermaid・参照シミュレーションの数値 | GitHub Actions（`ci.yml`） | 全 PR |
| L1 単体 | `TennisSim` の純粋な関数（物理・ソルバ・誤差・判定・スコア） | CQTest | 全 PR（C++ を含む PR） |
| L2 結合 | ワールドを使う（ストロークの同期・試合の進行・リプレイの一致） | Automation Spec ＋ `L_TestCourt` | 全 PR（夜間に全件） |
| L3 自動対戦 | AI 対 AI の長時間の試合（クラッシュ・ソフトロック・KPI） | Gauntlet（Beta）＋ コマンドライン | 毎晩、マイルストーンの終わり |
| L4 性能 | フレーム時間・メモリ・ヒッチ | Unreal Insights、CSV Profiler、Gauntlet | 週 1 回、マイルストーンの終わり |

## 6. リアリティ KPI の計測（AI 対 AI）

### 6.1 実行

```
UnrealEditor-Cmd.exe Tennis.uproject -game -nullrhi -unattended -nosound
  -ExecCmds="Tennis.AIvsAI Matches=50 Rules=DA_Rules_Tour Venue=DA_Venue_CenterHard Difficulty=Pro Style=Mixed TimeScale=8"
  -log -csvout=Saved/KPI/kpi_<日付>.csv
```

- 描画なし（`-nullrhi`）・時間の加速（固定ステップは維持）で、1 セットを 60 秒以内に実行する（FR-DBG-006）
- 毎晩、ハード・クレー・芝の 3 会場で 50 試合ずつ実行する

### 6.2 集計と判定

| KPI | 目標（Pro 対 Pro、ハード） | 根拠 |
|---|---|---|
| 0〜4 球で終わるポイントの割合 | 62〜78% | RES-03 §4 |
| 1 ポイントの走行距離（1 人） | 7〜13 m | RES-03 §2 |
| ラリーのフォアの平均回転 | 2,000〜2,800 rpm | RES-03 §1.1 |
| ラリーのフォアの平均球速 | 115〜135 km/h | RES-03 §1.1 |
| 第 1 サーブ（フラット）の平均 | 175〜200 km/h | RES-03 §1.2 |
| 第 2 サーブの平均 | 140〜165 km/h | RES-03 §1.2 |
| 第 1 サーブの確率 | 55〜70%（未検証の目安） | RES-03 §4 |
| ダブルフォルト | 1 セットに 0.5〜2 本（未検証の目安） | RES-03 §4 |
| 面による差 | 平均のラリー数：クレー > ハード > 芝 | RES-03 §4 |
| 凡ミスと強制されたミスの比 | 0.6〜1.6 | DD-04 §6.2 |

- 8 項目のうち 7 項目以上が範囲内で合格（NFR-REAL-003）
- 結果は CSV と、目標範囲を描いた箱ひげ図のレポート（HTML）で残す。前回からの変化が大きい項目を強調する

## 7. プレイテスト

| 回 | 時期 | 対象 | 見ること | 合格の目安 |
|---|---|---|---|---|
| PT-1 | M4 の終わり | 開発者＋テニス経験者 5 人 | 打感、タイミングの分かりやすさ、狙いの効き方、タッチの試作 | 「狙ったところに打てた」と感じる人が 4/5 以上 |
| PT-2 | M6 の終わり | 初心者 5 人・上級者 5 人 | 難易度（勝率）、AI の人間らしさ | Easy で初心者の勝率 70% 以上、Hard で上級者の勝率 50〜65% |
| PT-3 | M8 の終わり | 10 人（オンラインを含む） | 試合の流れ、UI、オンラインの違和感 | 重大な不満が 0 |
| PT-4 | M9（v1.0 の候補） | 20 人 | 全体 | アンケートの平均 4.0 / 5 以上 |

**記録**：プレイの動画、入力のログ、ミスの理由の分布、アンケート（打感・分かりやすさ・リアルさ・難しさ・また遊びたいか）。Visual Logger の記録を残し、気になった場面を再現できるようにする。

## 8. CI への組み込み（段階的に）

| 段階 | CI の内容 | ランナー |
|---|---|---|
| 今（2026-11-05 から） | `ci.yml`：L0（リンク・Mermaid・参照シミュレーション・プロジェクトファイル・秘密情報）。C++ ビルド用ワークフロー（非公開）：C++ のビルド（Development Editor）と `Tennis.` の全件（L1 と、`-nullrhi` で動く L2） | `ci.yml` は GitHub のホスト（ubuntu-latest）、C++ ビルド用ワークフロー（非公開） はセルフホストの Windows ランナー（W-1.10、#73） |
| M6 以降 | ＋ 毎晩の L3（AI 対 AI・KPI）と L4（性能） | セルフホスト（スケジュール実行） |

PR の作成者は、PR の前にも Unreal MCP の `AutomationTestToolset` で L1・L2 を実行し、結果を PR に貼る（開発ルール集（非公開） §7 の 2）。手順（`DiscoverTests` → `RunTestsByFilter("StartsWith:Tennis.")` → `GetTestResults`）と、PR に貼る要約の形は [ARCH-04 §6](../02_Architecture/04_Unreal_MCP_Workflow.md) を参照。

## 9. 不具合の管理

| 重大度 | 定義 | 対応 |
|---|---|---|
| S1 | クラッシュ、進行不能、セーブの破損、ルールの誤り | 直ちに修正。マイルストーンの完了を止める |
| S2 | 物理やルールの明らかな異常（まれ）、ネットワークの非同期 | 次のマイルストーンまでに |
| S3 | 見た目・音の不具合、UI の崩れ | 計画的に |
| S4 | 改善の提案 | バックログ |

- GitHub Issues で管理する。ラベル：`S1`〜`S4`、領域（`ball`・`shot`・`rules`・`ai`・`net`・`ui`・`art`・`audio`・`platform`）
- 不具合を直す PR には、再現するテストを先に入れる（コーディング規約 T-6）
